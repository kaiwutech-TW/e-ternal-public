# 各類所得扣繳 — 規格狀態與實作界線

status: **partial**（2026-07-30）
——**扣繳的帳務與年度取數已上線**；**只有憑單媒體檔的欄位格式規格未取得**，因此系統不產生媒體檔。

上一版（2026-07-27）把整件事寫成 `blocked-on-spec`，那是**過度封鎖**。
缺的規格擋住的只有「把資料輸出成財政部要的那個檔」，
擋不住「扣了多少、扣了誰的、全年合計多少、帳上還欠國稅局多少」——
而後面這幾件才是每天在發生、且沒有系統就只能靠翻紙本合約解決的事。

**一句話：取數已經有了，缺的只是輸出格式。**

## 本文件的紀律（使用者已拍板）

**系統提供結構與算術，稅率／級距／門檻一律由使用者填寫並附自己查到的依據。
系統絕不斷言任何稅率、免稅額度、繳納期限或憑單格式代號。**

違反這條的內容一律是缺陷——包括本文件自己（見下方第四節：本文件曾經斷言、現已降級的內容）。

## 一、已可動，且本批已做（不需要任何外部規格）

以下全部落地並有測試（`apps/api/test/withholding.test.ts`、`packages/core/src/withholding.test.ts`）。

### 1. 交易對象的個人／法人識別

`partners.is_individual`（boolean）＋ `partners.id_no`（身分證統一編號／居留證號）。
遷移：`packages/db/migrations/0015_withholding.sql`。

- **為什麼要分**：扣繳支出單只接受自然人。對法人付款沒有扣繳與年度憑單作業（該走進貨單或費用報銷），
  硬記進來會讓年度彙總混進不該申報的對象。
- DB 層 CHECK：**個人不得有統一編號**（`ck_partners_individual_no_tax_id`）——統編是營利事業的識別碼，
  個人填了它一定是資料錯置（最常見的是把房東本人與他名下公司混為一筆）。
- **`id_no` 是 PII，處理紀律**：不建索引、不進 `GET /partners` 的預設回傳（只回 `has_id_no`）、
  明文要走單筆專用端點 `GET /partners/:id/id-no` 且限財務／管理者、
  **不得出現在任何飛行紀錄、規格文件、匯出範例或測試 fixture 的真實值中**（本 repo 可能公開）。
- 之所以還是要存：不存的話，要填年度憑單時得回頭翻紙本合約——系統存了名字卻不存身分證號，
  等於把「申報用的資料來源」做成半套。

### 2. 扣繳類別與費率設定（**費率由使用者填**）

表：`withholding_categories`。畫面：「扣繳」頁的〈扣繳類別與費率〉（`apps/web/src/pages/Withholding.tsx`）。

| 欄位 | 意義 |
|---|---|
| `label` | 白話標籤，使用者自訂（例如「付給個人房東的租金」） |
| `expense_account_code` | 這一類的費用記到哪個科目；建立／修改時檢查科目存在且為費用類 |
| `tax_rate_bp` | 扣繳率，basis point（中性示例：3.5% ＝ 350）。**允許 NULL** |
| `supplement_rate_bp` | 補充保費率，同上。**允許 NULL** |
| `source_note` | **使用者自己寫的依據來源**（例如「依據 XXX 頁面，查詢日 2026-07-30」）。程式完全不驗證內容 |
| `active` | 停用後不再出現在建單下拉，但既有單據不受影響 |

紀律上的三個關鍵設計：

1. **費率允許 NULL，且刻意不給 DEFAULT 0**。`NULL` ＝「還沒查」，`0` ＝「我查過，這類不用扣」——
   兩者必須分得開。預設 0 會讓「沒設定」偽裝成「不用扣」，而使用者會以為系統已經替他判斷過了。
   畫面上 NULL 顯示為橘色的「尚未設定」，0 顯示為「0%」。
2. **種子類別只給標籤與科目對應，費率一律留空**：
   〈付給個人房東的租金〉→ 6121、〈付給個人的專業服務費（記帳、法律、設計等）〉→ 6124。
   種子放在 migration 而非 `seedAccounts()`——migration 每個資料庫只跑一次，
   使用者改了標籤或停用了類別都不會在下次重啟被蓋回去（扣繳類別從第一天起就是**使用者的資料**）。
3. **填了費率卻沒填來源，建單畫面會提示（不阻擋）**。理由寫在提示文字裡：
   明年這個數字若變了，你會需要知道當初是照哪裡填的。

費率上下限只擋物理不可能的值（0–10000 bp ＝ 0–100%），
用途是接住「把 10% 打成 1000%」這種打錯一個零的輸入，不是稅法判斷。

### 3. 扣繳支出單與自動分錄

表：`withholding_payments`。服務：`apps/api/src/services/withholding.ts`。

一張單同時記三件事：認列多少費用（`gross_amount`）、代扣多少（`tax_withheld`／`supplement_withheld`）、
實際付出去多少（`net_amount`）。自動拋轉**固定四行**：

```
借  類別對應的費用科目        gross_amount     （認列的費用是給付總額，不是實付額）
  貸  2211 代扣所得稅          tax_withheld
  貸  2212 代扣勞健保費        supplement_withheld
  貸  現金／銀行科目           net_amount
```

- **四行固定寫出（金額為 0 也寫）**：對帳的人要能一眼看出「這張單扣了多少、實付多少」，
  而不是靠某一行有沒有出現去推論。
- **為什麼不能用費用報銷代替**：報銷的 `claim.total` 是一個金額貫穿核准與付款兩張傳票，
  結構上記不了「認列 A、實付 B」。硬用報銷記淨額的後果是**費用少列、扣繳稅款憑空消失**。
- **算術只有一條**：給付額 × 使用者填的費率（`packages/core/src/withholding.ts` 的 `withheldByRate`，
  前後端共用同一份，避免兩邊算出不同數字）。費率為 NULL 時**回 `null` 而不是 0**。
- **試算值一律可覆寫**。小額給付的免扣門檻、身分別例外、跨月合併給付這些規則本系統**沒有模型**；
  硬算出來的數字看起來很權威卻可能和使用者手上的繳款單差一截，
  到那時「改不動」比「算錯」更糟——他只能放棄這張單改回手工傳票，
  於是年度憑單又回到沒有取數來源的狀態。覆寫時系統會在回應的 `notes` 說明「依費率試算 X 元、實填 Y 元」。
- 每一道驗證都給脫困路徑：對象不是個人 → 指到「客戶與商品」頁的個人勾選框，並說明若對方是公司該改用哪張單；
  費用科目被停用 → 指到扣繳設定改科目或到科目頁啟用；代扣合計超過給付額 → 提醒「給付總額要填扣繳前的金額」。

### 4. 年度彙總（申報各類所得憑單的取數來源）

`GET /withholding-payments/summary?year=YYYY`（`paymentSummary`）。

- 依 **「受領人 × 類別」** 分組，加總筆數、給付總額、代扣稅額、代扣補充保費、實付額，並有合計列。
- **依 `pay_date` 的年份歸年**，不是傳票日也不是建檔日——申報的所屬年度看的是給付這件事發生在哪一年。
- 回傳 `hasIdNo`（**不回身分證號明文**）：沒填的受領人在畫面上標紅字「未填」，
  因為那是會讓你填不出憑單的唯一硬缺口。明文要按「顯示」逐筆呼叫單筆端點。

### 5. 2211／2212 餘額顯示

`liabilityBalances()`：貸方為正 ＝ **已經從對方身上扣下來、但還沒繳出去**的稅款／保費。

- 不限日期也不限年度：這是「現在還欠國稅局／健保署多少」。
- 繳款後由使用者開手工傳票沖回（借 2211／2212、貸 銀行存款），餘額歸零。
- **刻意不回傳、也不顯示任何繳納期限**（見第四節）。
- 用 SQL 聚合而非撈回全部分錄，且 `SUM` 轉 text 再由 JS 轉數字——跨筆 SUM 是 bigint，
  `::int` 在累積多年的庫上會炸成 500 integer out of range。

### 系統明確**不做**的事

不內建任何費率／門檻／免扣額；不區分居住者與非居住者；不做任何適用性判斷；
不提示任何繳納或申報期限；不產生憑單媒體檔；不產生憑單列印；無薪資模組（Phase 5）。

## 二、仍然卡住的（只有這一件）

**憑單媒體檔的欄位格式規格。**

- 媒體檔為固定長度文字格式；**完整欄位表在申報軟體安裝包內附的格式說明文件**，公開網頁查不到全文。
- 沒有它就無法產出可被財政部申報軟體匯入的檔案，而**「能被官方軟體匯入」是本專案對這類功能的唯一驗收標準**
  （與 401 相同）。猜欄位長度做出一個匯不進去的檔，比不做更糟。
- **卡住的只有輸出**：第一節那五項都不依賴這份規格，所以它們已經上線。
  現況的使用方式是：本系統彙總 → 使用者抄進財政部的申報軟體。

### 取得規格的路徑（擇一）

1. tax.nat.gov.tw →「各類所得憑單(含信託)資料電子申報」→ 下載申報軟體（Windows）→ 安裝目錄內格式說明文件
   ——**與 401 申報軟體驗收同一台 Windows 機器可一次辦兩件事**。
2. 向所轄國稅局索取媒體申報檔案格式規格（扣繳申報專區）。
3. 若日後找到記帳士顧問，直接跟他要（他們的系統天天在產這個檔）。

### 取得後的實作邊界（先寫下來，動工時省判斷）

- 資料來源：**已經有了**——`withholding_payments` 的年度彙總（受領人 × 類別）就是媒體檔的取數來源，
  加上 `partners.id_no`。動工時要做的是「彙總 → 固定長度欄位」的對應與編碼，不是重新設計資料模型。
- **格式代號與所得類別的對應由使用者維護**：`withholding_categories` 是使用者自己建的類別，
  系統不會、也不該自行判斷某個類別屬於哪一種格式代號。
  屆時的做法是在類別上加一個**使用者填寫**的格式代號欄位（比照 `source_note` 的紀律：程式不驗證內容、不預設值），
  **不是**由系統內建一張代號對照表。
- 範圍第一批仍以居住者為限；非居住者的差異本專案未查證，且系統沒有身分別的模型。
- 驗收方式與 401 相同：媒體檔以財政部申報軟體**實際匯入通過**才算 `verified`。

## 四、本文件曾經斷言、現已降級的內容

⚠️ **舊版本文件（2026-07-27）在「已確認的事實」標題下，寫了三類本專案紀律明令不得斷言的內容**：

1. **憑單格式代號**與其所得類別的對應（列了四組代號並稱為「常見格式代號」），以及製單編號的組成規則。
2. **非居住者的就源扣繳率**（列了兩個百分比）。
3. **申報期限**（列了一個具體日期）。

這三類**已全部從本文件移除，且刻意不以任何新的數值取代**。理由與 `chart-of-accounts.md` 表 B2 完全相同：

- 它們沒有一級來源全文佐證（來源欄當時列的是入口頁與公告連結，不是格式規格書本身）；
- 這種寫法最危險的地方不是錯，是**看起來已經查證過**——後人會直接拿去當規格用，
  而本專案的紀律正是「法規原文為一級規格」；
- 更直接的矛盾：程式（`services/withholding.ts`、`pages/Withholding.tsx`）明白寫著
  「系統不提示任何繳納期限」「不產生憑單格式代號」，規格文件卻在斷言它們。
  **規格文件與程式對同一件事給出不同紀律，是文件的缺陷，不是程式的。**

需要這些數值時，由**使用者自己查證後填入系統的設定欄位**（費率填 `tax_rate_bp`／`supplement_rate_bp`
並在 `source_note` 註明依據；期限與格式代號目前系統不涉及）。
