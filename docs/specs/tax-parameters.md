## 一、這張表是什麼

在它之前，「稅率」在本系統有兩種存在形式，兩種都不對：

1. **寫死在程式常數裡**（`money.ts` 的 `VAT_RATE`、`expenses.ts` 的 `/1.05`、
   `invoices.ts` 的 `*1.05` 與 `taxRate: 0.05`、`purchase-orders.ts` 的 `calcTax(subtotal)`）。
   改一次要改程式並重新部署，一般使用者做不到；而且它偽裝成「系統知道正確答案」。
2. **寫在扣繳類別上**（`withholding_categories.tax_rate_bp`，migration 0015）。
   使用者填得動、也有來源欄——但它**沒有生效期間**。費率變動時只能覆寫，
   而覆寫掉的那一刻，去年的單據就再也解釋不出來了。

`tax_parameters` 補的正是第 2 點缺的那一塊：**同一個參數在不同期間可以有不同的值，而且兩個值都留著。**

| 欄位 | 意義 |
|---|---|
| `kind` | 參數種類。系統自己會讀的四種：`vat`、`income_tax`、`undistributed_earnings`、`input_tax_deductible`。**text 而不是 enum**——使用者查到我們沒想過的參數（查定課徵稅率、某類支出的列報限額）時，應該當場就能記下來，而不是等我們改 enum 再發版 |
| `scope_key` | 該 kind 需要細分時用。`input_tax_deductible` 用費用科目代號（`6137`）；`vat` 這種全公司一個值的留 NULL |
| `label` | 使用者自訂的白話名稱 |
| `valid_from` / `valid_to` | 生效期間，**兩端都含**。`valid_to` 為 NULL ＝ 仍有效 |
| `brackets` | 級距型的值（jsonb 陣列，見下節）。與 `bool_value` **恰好一個非 NULL**（DB CHECK） |
| `bool_value` | 布林型的值（例如可否扣抵） |
| `source_note` | **使用者自己寫的依據**。程式完全不驗證內容——驗格式只會逼人寫假的。但有值卻沒寫來源時畫面會提示（提示，不阻擋） |
| `entered_by` / `entered_at` | 誰在什麼時候填的。兩年後有人問「這數字哪來的」，`source_note` 回答「照哪裡填」，這兩欄回答「誰去查的」——而那個人通常還在公司，問得到 |

## 二、為什麼是 append-only

**這張表只新增、不覆寫、不刪除。** 法規變了是「新增一列 ＋ 把舊列的 `valid_to` 補上」。

理由不是資料潔癖，是**舊年度必須算得回來**：核定通知或更正申報可能兩三年後才來，
那時要重算的是「當年那個費率下的數字」。參數列被覆寫的那一刻，
過去每一張單據的稅額都會變成查不出來歷的孤兒——帳上寫著 50，系統現在算出來是 40，
沒有任何地方解釋得了 50 是怎麼來的。
（同一個紀律見 `.flightwake/DECISIONS.md` 的 append-only 體例，以及 `schema_migrations`
的「記錄哪些跑過」——都是「歷史必須留著」的同一件事。）

因此 API 只有 `POST` 與 `GET`：**沒有 PATCH、沒有 DELETE**。append-only 不是靠慣例維持的，是沒有那條路。

**「接續」（`supersedePrevious`）是唯一允許改動舊列的操作，而且只動 `valid_to`**：
新增一列時勾它，系統會把同一 `(kind, scope_key)` 中「仍涵蓋新列 `valid_from`」的前一列
的 `valid_to` 設為 `valid_from` 的前一天。舊列的值、依據、輸入者一律原封不動。

服務層另擋「同一 `(kind, scope_key)` 的生效期間重疊」，錯誤訊息會說出跟哪一列衝突
（列號、名稱、期間），並指出「勾接續」這條出路。

### 填錯了怎麼辦（脫困路徑）

**新增一列，從「更正生效日」起接續，並在依據來源欄寫明更正的是第幾列。**
如果那一列從第一天就填錯（新列的 `valid_from` 與舊列相同），接續會讓期間顛倒而被擋下——
訊息會把上面這條路徑講出來。

⚠️ **不論怎麼更正，都不會回頭重算已建立的單據**：稅額在建單當下就落地
（`sales.tax`、`purchases.tax`、`expense_items.tax`、退回單的 `tax`）。
需要更正既有單據的請自行判斷處理方式（沖銷重開，或開手工傳票調整）。

## 三、三種 mode 的算術定義

`brackets` 是陣列，每個元素 `{ from, to, mode, rateBp }`。
`rateBp` 是 basis point（萬分之一，3.5% ＝ 350）——整數運算避開浮點誤差
（與全系統「金額一律整數元」同一個理由），而 bp 而不是百分點是為了容納帶小數的費率。

三種 mode 都是**通用的算術形狀，不以任何特定稅制命名**。
命名成「小規模營業人」「營所稅」之類，會讓使用者以為系統知道該用哪一種——而它不知道。

| mode | 算式 |
|---|---|
| `exempt` | 稅額 ＝ 0 |
| `rate_on_total` | 稅額 ＝ **課稅基礎全額** × `rateBp` |
| `rate_of_excess` | 稅額 ＝ (**課稅基礎 − 該級距 `from`**) × `rateBp` |

結果四捨五入至整數元（沿用 `roundHalfUp`）。

**涵蓋規則**：`from <= base` 且 `to === null || base <= to`（兩端都含）。
邊界值同時落在兩級時（前一級的 `to` 等於後一級的 `from`），取 **`from` 較大的那一級**
——與口語的「超過 X 者適用下一級」一致，而且讓「剛好等於級距起點」有唯一答案。
沒有這條規則的話，同一個金額會因為陣列順序而算出不同的稅，那種錯誤不會有任何徵兆。

**算不出來時丟錯，不回 0**：空級距、`base` 落在級距之間的空隙、最高一級漏了「無上限」、
課稅級距沒填費率——全部丟錯，而且訊息說得出要補哪一段。
0 與「使用者還沒設定這一段」在畫面上長得一模一樣，而後者放行的後果是一張稅額為 0 的單據靜靜入帳。

單一費率（例如營業稅率）＝「一個涵蓋全區間的 `rate_on_total` 級距」，不另立欄位。
`flatRateBp()` 只認得這種形狀與單一 `exempt`；其他形狀回 `null`，由服務層走回退並說明理由。

## 四、系統實際會拿去算的兩種參數

其餘的 kind 系統**只保管、不計算**（見第五節）。

### 4.1 `vat` — 營業稅率

`resolveVatRate(db, 單據日期)` 依**單據日期**（不是今天）解析，交給 `calcTax(net, rate)`。
接線點（本批全部接上，每一處都有測試）：

| 路徑 | 解析用的日期 |
|---|---|
| 進貨 `createPurchase` / 銷貨 `createSale` | `docDate` |
| 報價 `createQuote` / 訂單 `createOrder` | `quoteDate` / `orderDate`（稅額只是**估價**，出貨時由 `createSale` 以出貨日重算） |
| 採購單 `createPurchaseOrder` | `orderDate`（同上，收貨時由 `createPurchase` 重算） |
| 銷貨退回／折讓、進貨退出／折讓 | **原單日期**（`sale.docDate` / `purchase.docDate`），不是退回日 |
| 報銷單內含稅回推 | `item.invoiceDate ?? claim.claimDate` |
| 發票 XML（B2C 明細含稅、`taxRate` 欄位） | `sale.docDate` |
| 401 的 B2C 拆算 `splitB2CTotal` | `invoice.invoiceDate` |

**退回單為什麼用原單日期**：`returnTax()` 整套邏輯（`origTax − priorTax` 的上限與軋平）
都在還原**原單**的稅額。用退回日的費率算，跨費率期間的退貨會把原單稅額沖不平：
原單以舊費率入帳 50、退回時以新費率算出 40，帳上永遠留著 10 元沖不掉的銷項稅——
而它會混在 2288 的餘額裡，直到申報時才發現對不起來，那時已經找不出是哪一張單。
（帳務歸期仍以退回日為準，`assertPeriodOpen` 看的是 `input.docDate`，那是兩件事。）

**`convertQuote` 刻意不重算**：轉單是把「談好的價」原封搬過來，客戶看到的總額不該
因為系統這一天解析到別的費率而變動。真正入帳的數字在出貨時重算。

#### 回退路徑（不可靜默）

找不到涵蓋該日期的 `vat` 參數、或那一列不是單一費率時，**不擋下建單**，
改用 `money.ts` 的 `VAT_RATE_FALLBACK` 並在回應帶 `taxNotes` 警告。

- 為什麼不擋：空的參數表（全新資料庫）或早於最早生效日的日期（補舊單）都不該讓系統壞掉。
  擋下的話使用者連第一張單都開不出來，而錯誤訊息指向的設定頁對「只想先試用看看」的人是一道死牆。
- 代價是必須**大聲**：`taxNotes` 一路回到畫面（進貨／銷貨表單、報銷、發票、401 申報頁），
  文字明說「這個預設值是本系統在稅法參數功能出現前一直在用的那個數字，**不是本專案查證的結果**」。

#### migration 種子的那一列

0016 種下**一列** `vat` 參數，值就是系統一直以來使用的那個費率，`valid_from` 刻意訂得非常早
（涵蓋資料庫裡已經存在的每一張單據，因為退回單會回頭用原單日期解析）。

`source_note` 寫著：
> 此列是既有行為的遷移（DECISIONS 2026-07-21 與官方範例 golden 測試），不是本專案的查證結果；請確認後補上你的依據來源。

**這是誠實的來源標註，不是斷言**——差別在於它說的是「這個值從哪裡來」而不是「這個值是對的」。
不遷移它的後果有二：① 既有資料庫的每一張新單據都走回退路徑並不斷跳警告
（雜訊會蓋掉真正的警告）；② 「首次啟動」與「升級上來」兩種資料庫行為不一致，
而那是最難察覺的差異。

#### 小規模營業人的查定課徵

**同一張表換一列即可**（`kind='vat'`、單一 `rate_on_total` 級距）。
系統**不 seed 任何這類數值**，只在維護頁說明可以這樣用。

### 4.2 `input_tax_deductible` — 報銷分類的進項稅可否扣抵

`scope_key` ＝ 費用科目代號，`bool_value` ＝ 可否扣抵。
`resolveDeductible(db, 科目代號, 報銷單日期, core 預設值)`：
**先查 tax_parameters，查不到才用 `EXPENSE_CATEGORIES` 的預設值**，以**報銷單日期**解析生效期間。

為什麼分類清單留在 core、只有這個布林值可覆寫：

- **分類清單是結構**。它餵養 `SYSTEM_ACCOUNT_CODES`（＝哪些科目停不掉、改不了碼）。
  搬成使用者資料的話，使用者刪掉一個分類，該科目下一次重啟就被 `seed.ts` 的反向校正
  設回 `is_system = false`、接著可以被停用，而已入帳的舊報銷單與 `approveClaim` 的
  `need(code)` 會在核准時丟 400／500。反過來，新增一個指向任意 6xxx 的分類會把那個科目
  **永久鎖成不可停用**，卻又不在 `seed.ts` 的校正範圍內（校正只涵蓋 `SEED_ACCOUNTS`），
  漂成「標了 `is_system` 卻不受保護」的中間態。
- **可扣抵性是稅法參數**，與結構無關——它才是該由使用者查證後填入、附依據來源的那一半。

`GET /expense-categories` 回傳生效值（`inputTaxDeductible`）**與**系統預設值
（`defaultDeductible`）**與**來源（`deductibleSource`: `parameter` / `default`）與依據
（`deductibleSourceNote`、`deductibleValidFrom`、`deductibleValidTo`），
報銷頁據此明白告訴使用者「這一類目前是用系統預設還是你設定的值」。

⚠️ 稅額在建單當下就落地到 `expense_items.tax`，**補設參數不會回頭重算已建立的報銷單**。

## 五、系統**不**做的事（界線）

- **不計算營所稅**。`kind='income_tax'` 存在，是為了讓你把查到的規則（級距、費率、生效期間、依據）
  記錄下來，**實際申報仍須你自行計算與填報**。系統沒有任何端點會去讀它。
- **不計算未分配盈餘加徵的稅**。`kind='undistributed_earnings'` 同上。
- **存了參數不等於系統會幫你報稅。** 維護頁把這件事寫在最前面的「這一頁做什麼、不做什麼」卡片裡，
  並在這兩種 kind 的分組標題下再講一次。
- **不判斷你填的數字對不對**。驗證只驗**結構**：日期格式、期間不顛倒、期間不重疊、
  級距不重疊、費率是 0–100% 的整數 bp、級距與布林值恰好一種。
  系統沒有立場說 3.5% 比 50% 合理，也不知道你要記的是哪一種稅。
- **不提示任何繳納或申報期限**。

## 六、權限

新 PageKey `tax-parameters`，只在 `admin` / `finance` 的 `ROLE_PAGES` 裡
（那兩個角色拿到全部 `PAGE_KEYS`；其餘四個角色是逐項列舉，因此自動排除）。
路由守衛 `apps/api/src/services/auth.ts` 的 `RULES` 有對應的一條——
不補那條會落到最後的 fallback「未列出的路由一律當管理頁看待」，
於是財務吃 403 而畫面上看得到這頁。

刻意不給 `gm`：這頁的每一次新增都會改變之後所有單據的稅額，唯讀給總經理沒有用途，
而多一個角色看得到就多一份「以為系統會自動報稅」的誤解來源。

## 七、已知的落差與風險

1. **沒有 `rate_bp_at_entry` 快照**（本批範圍外，設計已拍板不做）。
   落地的稅額（`sales.tax` 等）是可重現的，但兩條**讀取時再推導**的路徑不是：
   發票 XML 的 B2C 明細含稅、401 的 `splitB2CTotal`。
   使用者若日後編輯某一列的 `valid_to`（接續），這兩條路徑對舊發票的推導結果會跟著變。
   append-only ＋「只動 `valid_to`」已經把風險壓到很小（值本身不可改），但沒有壓到零。
2. **`convertQuote` 複製報價金額而不重算**：這是刻意的（見 4.1），但若報價與轉單之間跨了費率期間，
   訂單上的稅額會是報價當時的。出貨時會重算，所以不影響帳。
3. **`kind` 是自由文字**：打錯字會多出一種 kind。維護頁依 kind 分組列出，一眼看得見，
   但沒有「合併兩個 kind」的功能（append-only 之下也不該有）。
4. **參數表沒有「一次看到某天全站生效值」的檢視**：目前是依 kind 分組 ＋ 逐列標狀態。
   十人公司的參數列數以個位數計，暫不需要。
