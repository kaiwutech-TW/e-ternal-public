# tw_erp 分階段路線圖

> 目標：台灣中小企業的開源 ERP。差異化 = 真正做完法遵整合（電子發票、401/403、之後的薪資勞健保）＋ API-first ＋ AI Agent 接入。
> 市場前提（2026-07 調查）：沒有任何開源 ERP 開箱即用滿足台灣法遵；可參考的積木見 `docs/specs/` 內各規格書的參考清單。

## 貫穿全程的三條工作原則

1. **法規即規格**：每個法遵功能先寫規格書（`docs/specs/`），欄位對照到條文出處；開源專案（django-taiwan-einvoice、Dolibarr 模組、Odoo l10n_tw）只用來對答案，**不一致處＝回頭查法規的訊號**。GPL/LGPL 專案只讀邏輯、不抄程式碼。
2. **垂直切片**：每個里程碑是一條端到端打通的線（例：一張 B2C 發票上傳測試環境成功），不是一層做完的模組。
3. **驗證金字塔**：CI 內 golden-file 測試（XSD、媒體檔格式）→ 財政部官方測試環境實測 → 記帳士/會計師審規格書。程式碼審查驗不出法遵正確性。

## Phase 0 — 開案地基

- [ ] **技術棧決策**（後端/前端/DB）→ 寫入 DECISIONS.md
- [ ] **專案授權條款決策**（AGPL 防顧問公司圈地 vs MIT 最大化採用）→ 這是戰略選擇，寫入 DECISIONS.md
- [ ] Repo 骨架 + CI + API-first 邊界原則（核心領域 vs 法遵 adapter 分離）
- [ ] `docs/specs/` 規格書框架＋法規對照表（traceability：功能 ↔ 條文 ↔ 測試）
- [ ] 收集一級資料：MIG-4.1 規格書與官方 XSD、401/403 申報書與媒體檔格式、企業會計準則（EAS）科目
- [ ] 用自己公司統編申請大平台帳號＋ Turnkey 測試環境（開發期就能打真平台）
- [ ] 找一位記帳士/會計師當法遵顧問

**驗收**：規格書框架能回答「這個欄位是哪條法規要求的」；測試環境帳號可用。

## Phase 1 — 交易核心（進銷存＋最小會計）

- [ ] 主檔：商品、客戶、供應商（含統編驗證）
- [ ] 單據流：採購 → 進貨 → 銷貨 → 庫存異動
- [ ] 最小會計：台灣會計科目表、單據自動拋轉傳票、日記帳/總帳
- [ ] API 全覆蓋（之後 AI Agent 與行業模板都長在這組 API 上）

**驗收**：一條「進貨→銷貨→庫存→傳票」流程端到端走通，全程走 API。

## Phase 2 — 電子發票（第一個法遵垂直切片）

- [ ] **里程碑 2a（最優先）**：一張 B2C 發票 → MIG-4.1 XML → 過官方 XSD → Turnkey 上傳測試環境成功
- [ ] 字軌配號管理、作廢、折讓、B2B 存證/交換、載具/捐贈碼
- [ ] Adapter 架構：Turnkey adapter（客戶自建、自己憑證）｜加值中心 adapter（綠界/Amego/藍新，參考 paid-tw/einvoice 的抽象）
- [ ] Golden-file 測試進 CI（每種單據情境一份標準 XML）

**法規紅線**：每家客戶用自己的憑證傳輸；**絕不做集中代傳**（那會讓我們變成加值中心，需 ISO 27001＋資格審查）。

**驗收**：全部發票情境在官方測試環境實測通過。

## Phase 3 — 營業稅申報（401/403）

- [ ] 進項發票登錄與扣抵管理（401 的另一半，別只做銷項）
- [ ] 401、403（兼營）申報媒體檔輸出
- [ ] 驗證：媒體檔能被財政部電子申報繳稅軟體成功匯入
- [ ] 記帳士顧問審整份申報規格書

**驗收**：一個完整雙月期的實際資料 → 產出媒體檔 → 申報軟體匯入成功。

## Phase 4 — 生態與協作

- [ ] 記帳士匯出格式（傳票/明細，讓記帳士推薦我們，不是取代他們）
- [ ] 各類所得扣繳申報（薪資/租金/勞務報酬扣繳憑單；**申報期間請自行查證，系統不提示**）
- [ ] API 公開文件 + **MCP server**（AI Agent 接入第一步，薄薄一層長在既有 API 上）
- [ ] 社群基礎：貢獻指南、部署文件、討論區

## Phase 5 — 人資薪資（刻意延後）

- [ ] 帶生效日期的「法規資料包」架構（勞健保級距、基本工資、勞退提繳率、二代健保費率——年度更新只發資料不改程式；**資料包本身仍由使用者填值與依據，系統不隨附任何法定數字**）
- [ ] 薪資計算、勞健保投退保、扣繳憑單串回 Phase 4

**延後理由**：薪資是永久維護承諾而非採用關鍵；中小企業現有替代方案多。

## Phase 6 — 行業模板

- [ ] 模板機制（科目、單據、報表的行業預設組合）
- [ ] 首 2–3 個行業（依早期使用者選）

## AI Agent 軌（並行，不是獨立 phase）

Phase 1 起 API-first → Phase 4 MCP server → 之後逐步加 agent 工具與社群分享的 agent 情境。原則：agent 永遠只透過公開 API 操作，不走後門。
