# Agent UX 缺口盤點：哪裡最該把 agent 帶入、減少人的操作

> **定位**：這份是「總覽」。它回答「從使用者的角度，這套 ERP 哪些流程還是傳統 ERP 手感、
> 哪裡該帶入 agent」。每一條「帶入 agent」的詳細設計，落在 `deepseekHarnessDoc/`（DeepSeek
> Harness 的設計貢獻，供 Claude／Codex 三方審閱）。
>
> **前提共識（先讀）**：這套系統的法遵與資料正確性已經做到位；agent 的價值不是「做更多事」，
> 而是「把重複的鍵盤動作收進一句話或一張照片，但每一筆會動帳的動作仍然停在
> 覆述 → 人確認 → 系統執行 → 留軌跡」。這是蘋果式的「減少流程、不削弱安全」。

---

## 一句話結論

agent 今天只是一個「**讀資料 + 直接建立報價單 + 送 HR 申請**」的側欄；後兩者目前直接 POST，
尚未符合較新的 proposal／accept 責任模型。其餘流程仍有不少「人一格格填、一張張點」，但占比
尚未量測。最後一哩路不是加功能，是把**高頻、多步驟、
出錯代價高**的那幾條流程，從「人做完每一格」變成「agent 備好草稿、人只按確認」。

---

## 一、判斷框架：什麼叫「傳統 ERP 手感」

一個流程若同時具備下面特徵，就是 agent 該接手的地方：

1. **高頻**：每個人、每天／每週都在做。
2. **多步驟**：同一筆事實要跨多張單、多個頁面、多段狀態轉移。
3. **欄位可從外部事實推導**：金額、日期、統編、品項本來就在一張照片／一段對話／一份
   銀行匯出檔裡，人只是「搬運工」。
4. **出錯代價高**：錯一格＝少抵稅、補稅罰款、帳齡失準、催錯款。
5. **低判斷、高重複**：FIFO 沖最舊、到期提醒、格式代號分流——規則明確，不需要會計專業判斷。

對照組（**不該**交給 agent 的）：會計科目歸屬的最終決定、稅率與申報期限、核准過帳、
關帳——這些是 soul.md 三條底線，交給人是對的，agent 只能「建議＋覆述＋等確認」。

## 二、現況盤點：agent 今天已覆蓋哪些

| 能力 | 內建側欄（`agent-chat.ts`） | MCP（`mcp/src/tools.ts`） |
|---|---|---|
| 讀資料 | ✅ `api_get`（全 GET） | ✅ 16 工具含三大報表 |
| 建立報價單 | ⚠️ `create_quote` 直接 POST 正式 open 報價，待遷 proposal 契約 | ✅（同樣是正式寫入） |
| 送請假／加班／補卡 | ✅ `create_hr_request` | ❌ |
| 公司記憶／操作指南 | ✅ `read_memory`／`search_memories`／`propose_memory`／`read_guide` | ❌ |
| 報價轉訂單 | ❌ | ✅ `convert_quote` |
| 出貨 | ❌ | ✅ `ship_order` |
| 核准報銷 | ❌（內建側無此工具；`DECISIONS.md:9`：寫入一律人按確認） | ⚠️ `approve_expense_claim` |
| 進貨／收貨／開發票／收付款／合約請款／固定支出／扣繳／盤點／發薪 | ❌ 全部只能「看」 | ❌ |

所以「帶入 agent」的戰場，是下面這些**現在完全靠人手**的流程。

> ⚠️ 責任方向已由 `.flightwake/DECISIONS.md:9` 定案：agent 只能提案、人按確認才生效；目前
> `create_quote`／`create_hr_request` 直接 POST，MCP 又有 `approve_expense_claim`、`ship_order`、
> `convert_quote`，都仍待 proposal 契約與工具面同步，不能把現況稱為結構紅線已完成。

## 三、痛點地圖（依「頻率 × 操作步數 × 出錯代價」排序）

### A. 日常高頻 × 全公司（優先假設，待 W0 量測）

**A1. 費用報銷：從「拍完照還要填一堆欄位」→「拍一下就送件」**
- 現在：QR 成功時號碼／日期／金額／統編會帶入，但分類仍手選；QR 失敗或紙本收據則多欄手填。
- 帶入後：拍照 → 解析 QR 所載的統編／日期／金額／品名 → 顯示歷史賣方分類候選但不自動選中 →
  員工核對用途與欄位後送件。紙本 OCR 另受 vision 明示同意控制。
- 詳細設計：`deepseekHarnessDoc/expense-claims-agent.md`。

**A2. 進貨發票登錄：401 進項的生命線，漏一筆就少抵稅**
- 現在：收到供應商發票 → 人工登錄號碼、發票日期、格式代號、扣抵代號。
- 帶入後：拍照 → 自動對到哪張進貨單 → 建議格式代號／扣抵代號 → 人確認。
- 這是「出錯代價最高」的一格（補稅＋罰），agent 不只省步驟，還擋錯。

**A3. 收付款對帳：補上缺口 R7**
- 現在：SOP 每月作業第 2 步「對現金」是純人工比對銀行 vs 該銀行帳戶綁定科目
  （種子預設為 `1103 銀行存款`，不得在對帳本體寫死）。
- 帶入後：匯入銀行匯出檔 → agent 建議這筆匯款沖哪幾張（FIFO 最舊）／溢收掛預收 → 人確認。
- 詳細設計：`deepseekHarnessDoc/bank-reconciliation-agent.md`。

### B. 日常高頻 × 業務／財務（需覆述確認，中風險）

**B1. 銷售「一句話變報價／訂單」＋整鏈 wizard**
- 現在：業務把 Line／Email／電話內容手動翻譯成報價 → 轉訂單 → 出貨 → 開發票 → 收款，五段都人點。
- 帶入後：貼一段對話 → agent 抓出客戶／品項／數量／單價／交期 → 報價草稿；
  成交後把「出貨 → 開發票 → 收款」串成一條確認流（每張單覆述 → 確認 → 下一張）。
- 已有直接 POST 的 `create_quote`，但要先遷 proposal／accept；之後才談外部輸入解析與多段 chain。

**B2. 「該做什麼」從「人去查」變「登入後站內 briefing」**
- 現在：應收逾期、合約待請款、固定支出到期、字軌快用完、下期字軌未建——全要人去翻頁。
- 帶入後：登入首頁顯示「今天你該做這幾件事」；第一版不做站外推播，避免通知狀態、去重、
  角色、時區與退訂成本。
- 這才是 README「E直在線——系統永續在線，不是你」從口號變功能的最後一哩路。

### C. 低頻 × 高壓力（agent 做「預檢」不是「代辦」）

**C1. 月結／401 的「預檢 agent」**
- 現在：`checkPeriod()` 已有五項月結檢查，但覆蓋仍不足；401 產生後仍有人工補登項目
  （退回折讓媒體檔、零稅率通關方式、退稅欄、兼營被擋）。
- 帶入後：月結前 agent 自動跑健康檢查——試算表平不平、折舊提了沒、庫存帳 vs 存貨科目、
  報銷待核、缺證明單退回、字軌剩餘——列出「有問題的清單」，人只處理異常。
- agent 只檢查、只報告；關帳、申報本體永遠人手按。

**C2. 導入 wizard（一次性，但決定有沒有人願意開始用）**
- 現在：首頁已有六步 GettingStarted，SOP 是另一套八步，步驟與完成條件已漂移。
- 帶入後：agent 引導照順序走、每步檢查完成條件、缺哪步就說「你還沒設發票字軌，去設定頁」。

## 四、最後一哩路：初始假設（待 W0 翻案）

1. **報銷拍照 → 草稿**（使用面可能最廣、第一印象；仍待 W0 量測）
2. **銀行對帳 + 沖帳建議**（補 R7、帳務價值最高、spec 已定「只建議不自動確認」的安全邊界）
3. **站內「今天該做什麼」briefing**（先量需求，不預設站外推播成本最低）

前兩者的落地設計寫在 `deepseekHarnessDoc/`，第三個屬於「對話推播」的產品形態，尚未展開。

## 五、安全紅線（本文件所有建議都踩在同一條線上）

- agent **只備草稿、只建議、只報告**；核准、過帳、關帳、申報、作廢的「門」在人手上。
- 金額／統編／日期等**事實欄位**只來自可追溯來源（QR 所載值、銀行檔、使用者口述）；QR parser
  目前未驗證加密驗證資訊，不能把「可解析」寫成「已驗真」。
  agent 不得在辨識不確定時**猜**，只能留白並問。
- 外部 agent 的 API key 走所屬專用帳號 ACL；內建助理沿用目前登入者身分。兩者都需 proposal
  契約才能證明有人按過確認，憑證種類或操作日誌本身不等於人類 presence。
- 稅率、申報期限、科目最終歸屬，agent 永不代為決定（soul.md 底線一、二）。
