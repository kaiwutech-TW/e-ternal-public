# 對帳 agent 設計：匯入對應／比對敘事／補傳票草稿，只建議不自動確認

> **狀態**：收斂草案 v0.2（三方審閱後同步；待主導者排程與真實樣本）｜ 對應總覽：
> [`docs/agent-ux-gap.md`](../docs/agent-ux-gap.md) A3。
> **前置**：本功能目前**未動工**（缺口 R7）。對帳**本體**的規格在
> [`docs/specs/bank-reconciliation.md`](../docs/specs/bank-reconciliation.md)，三條邊界已定，
> 這份只設計**疊在本體之上的一層 agent**，不重新設計本體。

---

## 0. 先讀規格的三條邊界（agent 層踩死這三條）

1. **匯入不寫死銀行格式**：每帳戶一份「匯入對應檔」（哪欄是日期／收支／摘要／餘額，
   民國或西元、Big5 或 UTF-8）——對應檔是資料不是程式。
2. **明細列 append-only**：原始列原樣保存，重複上傳防重。
3. **比對只建議、不自動確認**：金額精確＋日期視窗列出建議，**人點了才算對上**；
   「自動確認會把金額剛好相同的兩筆不同交易悄悄配對，錯了零徵兆」。

外加規格第 4 點：**科目由使用者選，系統不猜**。

agent 在對帳裡的價值，恰好長在規格自己承認的最痛處——**「資料怎麼進來」**（台灣沒有
統一銀行明細格式），以及比對之後的**人話說明**。下面三個切入點。

---

## 1. 切入點一：匯入對應檔的 agent 輔助（打最痛的點：每家銀行格式不同）

### 1.1 現在（規格承認的痛）

規格第三節第 1 點：匯入要做成「每帳戶自設對應檔」。但對**非技術使用者**，自己設定
「哪一欄是日期、哪欄是收支、民國還西元」本身就是門檻——一設錯，後面比對全錯。

### 1.2 agent 帶入後

- 使用者上傳銀行匯出檔（CSV／xlsx，後者待議）→ 本機確定性 profiler 先讀必要資料列，
  算出欄位型別、日期格式、編碼特徵與正負號形狀；預設**不把原始交易列送給 agent**。
- agent 回一份**建議的對應檔**：
  - 日期欄是哪一欄、民國或西元、`/` 或 `-` 分隔；
  - 金額欄是一欄帶正負、還是收入／支出兩欄；
  - 摘要欄、餘額欄；
  - 編碼（Big5／UTF-8；由本機 profiler 判斷）。
- 使用者**逐項確認／改**，存成該帳戶的對應檔（資料，不是程式）。之後同一帳戶的檔案
  直接套用，不用再問 agent。

### 1.3 為什麼這條特別適合 agent

確定性 profiler 先處理可重現的編碼／日期／數字形狀；只有剩餘歧義才讓 agent 用白話詢問使用者，
不是讓 LLM 重算格式。agent 在這裡是**設定助手**，不是帳務執行者。

### 1.4 安全

- agent 只輸出「欄位對應建議」，不匯入明細、不建單；人確認後才存 mapping。
- 匯入與比對仍走本體的確定性引擎（spec 邊界 1、2）；mapping 確認前必須用預覽列顯示解析後
  日期、收支、摘要與餘額，錯誤 mapping 不能直接進正式匯入。
- 預設不把原始交易列送給 agent；若未來要另開 opt-in，必須與 vision 同樣綁實際 endpoint 並明示同意。

## 2. 切入點二：比對建議的「人話敘事」（不自動確認，只講人話）

### 2.1 現在（本體做完後，人會看到什麼）

確定性引擎（金額精確＋日期視窗，含一對多拆分）吐出一串「建議對上」與「兩邊對不上」。
畫面上若只是兩張清單，使用者要自己看懂「這筆 30,240 建議沖哪幾張、為什麼」。

### 2.2 agent 帶入後

agent 把引擎已產生的 evidence 翻譯成人話；反常條件也由確定性引擎標出，不由模型另算：

- 「7/5 銀行入帳 30,240，建議沖銷貨單 #12（20,000）＋#13（10,240），對象是『禾昇食品』。」
- 「這筆 8,000 銀行手續費**帳上沒有**——要不要我幫你起草一張傳票？」
- 「⚠️ 7/8 有一筆 50,000，金額跟銷貨單 #15 相同，但**對象對不上**（銀行摘要寫別家），
  建議不要自動配對，請你確認。」
- 「帳上有 3 筆、銀行沒有 → 是**在途存款／未兌現支票**，進調節表滾動。」

### 2.3 安全（這條是 agent 最該守住的地方）

- **agent 絕不替人點「確認對上」**。spec 邊界 3 的「自動確認＝錯配零徵兆」正是 agent
  最容易越界的地方——要寫進 soul 的對照規則：對帳的「確認」跟「核准過帳」同級，
  只有人能按。
- agent 只產**敘事**（哪些建議、哪些反常、哪些該補帳），不產任何單據、不寫任何對帳狀態。

## 3. 切入點三：bank-only 補傳票草稿（科目不猜，人選）

### 3.1 現在（規格邊界 4）

「銀行有、帳上沒有」的項目（手續費／利息／代扣）→ 快速建手工傳票；**科目由使用者選，
系統不猜**。

### 3.2 agent 帶入後

- agent 把 bank-only 項目整理成**傳票草稿**：「借（待你選的費用科目）、貸
  `[本次銀行帳戶綁定的科目代號＋名稱]` 8,000，日期 7/5，摘要『銀行手續費』」；銀行側一律取
  帳戶綁定的 `accountId`，連範例都不寫死代號（C-9）。
- **科目那格留空**，使用者從下拉選（soul.md 底線二「不替使用者決定會計科目歸屬」）。
- 人按下送出 → 走既有 `POST /journal-entries`（`createManualEntry`，含 `assertPeriodOpen`、
  停用科目擋、`assertBalanced`）。agent 只備草稿、不送。

### 3.3 需要的頁面入口

傳票頁提供純建議入口，回傳「借貸明細 + 科目代號留空待選 + 摘要」並填進當頁表單，由人送出；
不做伺服器端無法回填 browser state 的 `draft_journal_entry` agent tool，也不 POST 正式傳票。
這跟報銷設計的 OCR 建議是同一種「結果停在 browser state」的形態（見報銷設計 2.4）。

---

## 4. 產出與月結出聲（對照規格邊界 5）

- 本體產出「銀行存款調節表」（每帳戶每月），掛進月結檢查。
- agent 把調節表翻成人話：「這個月你有一筆 8,000 手續費還沒入帳、三筆在途存款、一張
  未兌現支票——入帳後調節表才會平」。
- 關帳前不平**出聲**（規格：提示不硬擋），agent 只是這個「出聲」的講人話版本。

---

## 5. 未決問題（給審閱者）

1. **前置依賴**：已收斂採 D5 三分法。手動勾對、調節表 model、候選引擎與狀態邊界可先做；
  profiler 只可用合成 fixture 做 spike；mapping schema、sniffer 規則、CSV/xlsx 範圍與完成宣稱，
  必須等至少一份真實去識別化匯出檔驗證。
2. **樣本去識別化**：已收斂為**預設只送本機算出的型別與形狀摘要**
  （欄位型別、日期格式、編碼特徵、正負號形狀），**不送原始交易列**——民國／西元、Big5／UTF-8、
  一欄帶正負 vs 收支兩欄只能從資料列判斷，但判斷結果可以本機算好再送，原始數字不外送。
3. **xlsx**：規格未決（CSV 一定收、xlsx 待看）。agent 推對應檔與收不收 xlsx 正交——
  xlsx 解析是確定性依賴問題，不是 agent 問題，照規格待定。
4. **比對建議的引擎與 agent 的邊界**：已收斂為確定性引擎產「建議對／對不上＋可驗 evidence」；
  agent 只做敘事，不改建議清單。不加模型生成的 `confidence`；若需 anomaly，必須是可重現的規則命中。
5. **傳票草稿形態**：已收斂為頁面純建議入口，草稿只進 browser state，不直接 POST。
