## 2. 歷史可算的兩項——逐欄定義

### 2.1 每張報銷單的明細筆數

| 欄位 | 內容 |
|---|---|
| 定義 | `expense_items` 依 `claim_id` 分組的列數；LEFT JOIN，所以 0 筆的空單也在母體裡 |
| 資料來源 | `expense_items`、`expense_claims`（`packages/db/src/schema.ts` 的 `expenseClaims` / `expenseItems`） |
| 母體 | `voided_at IS NULL` 的報銷單（作廢單另列一欄計數，不混進分布） |
| 觀測期間 | 由 `min/max(claim_date)` 與 `min/max(created_at)` 一起印出——兩者不同義，報銷日是使用者填的，建立日才是系統時間 |
| 樣本數 | 隨輸出逐項附上（`樣本數_單`） |
| 統計量 | min / max / 平均 / 中位數 / p90，另加一張直方圖（0、1、2、3、4、5-9、10+） |
| 正式庫數值 | **未取得**（環境未起） |
| 示範庫數值 | 樣本數 2 單，兩單的明細筆數分別是 1 與 2（照 §5.2 的硬規則只報原始計數，n=2 不報中位數／p90 這類彙總量）。**樣本不足，不做任何解讀** |

**這個數字要拿去回答什麼**：W6（報銷批次上傳）的價值直接綁在這裡。
如果真實資料的中位數是 1，「一次選多張」救的是少數人；如果 p90 是 8，批次上傳就是主線。
現在兩個假設都沒有證據。

### 2.2 明細的「解析成功率」

| 欄位 | 內容 |
|---|---|
| 定義 | `doc_type = 'einvoice'` 的明細數 ÷ 明細總數 |
| 名稱 | **解析成功率**。不是「原件有 QR 的比例」，見下方紅字 |
| 資料來源 | `expense_items.doc_type`（enum `expense_doc_type`：`einvoice` / `receipt` / `other`，`schema.ts:51`） |
| 母體 | 未作廢單的所有明細 |
| 觀測期間 | 同 2.1 |
| 正式庫數值 | **未取得** |
| 示範庫數值 | 樣本數 3 筆明細（einvoice 1、receipt 2）。**樣本不足，不引用百分比** |

> **命名警告（這一條錯了，整個結論就反了）**
> `receipt` 是解析失敗時的 fallback，同時裝著兩種完全不同的世界：
> ①這張憑證本來就沒有 QR；②有 QR 但沒掃出來——後者正是 W1 要修的雙碼缺陷
> （`einvoice-qr.ts` 單次 `jsQR()` 只回一個碼，右碼以 `**` 起頭被判 `null`）。
> 兩者在資料庫裡長得一模一樣。把 `receipt` 讀成「使用者的憑證多半沒有 QR」，
> 會把**我們自己的解碼缺陷**記成**使用者的憑證特性**，於是 W1 被降級、W15（vision OCR）被升級——
> 剛好是相反的順序。

### 2.3 附帶事實：W7 的冷啟動有多冷

腳本同時印出「出現過的賣方統編數／有統編的明細數／明細總數」。
理由：W7（歷史賣方分類候選）唯一能當 key 的欄位是 `seller_tax_id`，
而**只有解析成功的明細才有這個欄位**。所以 W7 的可用覆蓋率上限＝解析成功率，
而解析成功率又受 W1 的缺陷壓低。這是一條依賴鏈，不是兩個獨立的數字。

## 3. 執行方式

```sh
./scripts/w0-expense-baseline.sh          # 需要 docker compose 的 db 容器在跑
BASELINE_CONTAINER=<容器ID> ./scripts/w0-expense-baseline.sh   # 容器名不同時覆蓋
```

連法沿用 `scripts/backup.sh`：`docker exec` 進 db 容器跑 `psql`，
不需要 `DATABASE_URL`，密碼也就不必進這支腳本的環境。

**只讀是機器保證，不是人眼保證**：SQL 第一句把整個 session 設成
`READ ONLY`，日後若有人在裡面加一段 UPDATE，那會是硬錯誤而不是靜默生效。

## 4. 歷史算不出來的三項——為什麼不算

### 4.1 從拍照到送出的秒數

沒有任何一張表存過「開始」的時間點。`expense_claims.created_at` 是**送出成功的那一刻**，
拍照、掃描、重掃、選分類都發生在瀏覽器裡，一列都沒留下。
用 `created_at` 的間隔去估，估的是「兩張單之間隔多久」，不是「一張單花多久」。

### 4.2 真正無 QR 的比例

見 §2.2 的命名警告。資料庫裡不存在「原件上有沒有印 QR」這個觀測值，
只存在「我們有沒有解析成功」。要分開兩者，必須有人拿著原始憑證用眼睛看。

### 4.3 分類初選 → 最終值的改選率

兩道獨立的關卡各自就足以擋死：

- **重送會刪掉證據**：`apps/api/src/services/expenses.ts` 的 `resubmitClaim`（R11）
  對被退回的單是「刪舊插新」——`tx.delete(expenseItems)` 之後整批 insert。
  註解寫得很清楚，逐筆 diff 只會生出「改了金額沒改稅額」的半套狀態，所以是刻意的設計。
  代價就是舊分類一列不留。
- **audit 依隱私紀律不記 body**：`apps/api/src/services/audit.ts` 開頭
  「預設什麼都不記，只記結構性的事實」——誰、何時、什麼 method 打了什麼 path、幾號狀態碼。
  連 201 的回應也只白名單抓一個 `id`。所以沒有欄位級 diff 可以反推。

這兩條都不該為了量測而改。要改選率，就走 §5 的前瞻抽樣或明示遙測。

## 5. 前瞻抽樣要怎麼做

### 5.1 量哪幾個數字

| # | 指標 | 定義（要可判定，不能是「感覺快不快」） | 怎麼量 |
|---|---|---|---|
| M1 | 單張憑證從拍照到明細落地的秒數 | 按下拍照 → 該筆明細出現在草稿列表 | 人工計時（旁邊拿碼錶）或前端埋點記 `t0/t1` |
| M2 | 一張單從開始到送出的秒數 | 進入報銷頁 → 送出成功 | 同上 |
| M3 | 真正無 QR 的比例 | 人眼看**原始紙本**：上面印了 QR 嗎 | 人工檢視，與同一批憑證的解析結果配對 |
| M4 | 掃描失敗率 | 原件有 QR（M3 判定）但系統落成 `receipt` | M3 的配對表直接得出 = W1 的實際傷害面 |
| M5 | 分類改選率 | 系統/歷史候選給的初值 ≠ 送出時的值 | 前端埋點：記「初值」與「送出值」兩個科目代號 |
| M6 | 會計端事後改分類率 | 財務在核准前改掉的比例 | 人工記錄或審核頁埋點 |
| M7 | 每單張數 | 一次報銷帶了幾張憑證 | 已可從歷史算（§2.1），抽樣時只需交叉驗證 |

**埋點的紀律**：M5/M6 記的是**科目代號與時間戳**，不是 body。
不要為了量測破 `audit.ts` 那條「不記 body」——另開一張明確用途的量測表，
欄位只有必要的那幾個，並且講清楚保存期限。

### 5.2 樣本數要多少才算數

先講一條硬規則：**樣本不足就寫「不足」，不要補百分比、不要外推。**

| 指標 | 最低可用樣本 | 理由 |
|---|---|---|
| M1/M2（秒數） | 每人 5 張以上 × 至少 3 人 ≥ 20 張 | 秒數的變異來自人與憑證兩個來源，單一個人的 20 張只量到那個人 |
| M3/M4（QR） | ≥ 50 張原始憑證，且來自 ≥ 5 家不同賣方 | 這是比例估計；50 張時 ±10 個百分點左右的不確定性已經是能承受的下限，再少就只能報原始計數（「50 張裡 7 張沒有 QR」），不報百分比 |
| M5/M6（改選率） | ≥ 50 筆明細，且跨 ≥ 2 個月 | 月初月底的費用組成不同 |
| M7 | 全量歷史（不抽樣） | 已可直接算 |

樣本數低於上表時，報告一律寫成「**n = 12，不足以估計比例；原始計數為 …**」，
不寫百分比。這是 W0 驗收的重點條款。

### 5.3 量完之後可能翻案哪幾包

| 工作包 | 目前的排序依據 | 什麼結果會翻案 |
|---|---|---|
| **W6 批次上傳** | 直覺：「大家都一次交一疊」 | M7 中位數 = 1 且 p90 ≤ 2 → W6 從批次 1 降級（它有記憶體尖峰、整批 POST 過大等一串護欄成本，服務不到人就不值得付）。反之 p90 ≥ 5 → 升為主線 |
| **W7 歷史分類候選** | 直覺：「省下選分類的時間」 | M5 很低（初值幾乎都被接受）→ 候選解的不是真問題，W7 降級；M5 高但 M6 也高（人選錯、會計改回來）→ W7 的價值從「省時間」變成「省會計的返工」，驗收條件要跟著改。另外 §2.3 的覆蓋率若很低（有統編的明細占比小），W7 對多數明細根本不會觸發 |
| **W15 vision OCR** | 直覺：「紙本沒 QR 就得靠 OCR」 | **這一包最容易被誤判**。M3 低（真正無 QR 的憑證很少）而 M4 高（多半是掃不到）→ 真正該做的是 W1，W15 的價值大幅縮水，排最後是對的甚至可以不做。只有 M3 本身就高，W15 才有主線價值。這正是不能拿 `receipt` 比例當「無 QR 比例」的原因 |

W0 的結論**不延後** W2／W3／W4 這類已證實的正確性修復——那些有測試可證的缺陷不需要使用量數據背書。
