# 報銷 agent 設計：拍照 → 草稿 → 確認 → 送件，核准門在人手上

> **狀態**：收斂草案 v0.2（三方審閱後同步；待主導者排程）｜ 對應總覽：
> [`docs/agent-ux-gap.md`](../docs/agent-ux-gap.md) A1。

## 0. 先講結論（誠實盤點）

報銷已有「影像縮圖＋單次 QR 解碼＋欄位帶入」骨架，但 W1／W2 尚未收掉前不能用百分比宣稱
完成度。這份設計的重點是精確指出剩餘摩擦與正確性缺口，而不是重新提一次「做 OCR」。

| 步驟 | 現況（讀完 `Expenses.tsx` + `einvoice-qr.ts` 後的結論） |
|---|---|
| 拍照 | ✅ 已有 `readReceiptImage(file)`：縮圖 + QR 解碼一次完成 |
| 電子發票 QR 解碼 | ✅ 已有 `parseEInvoiceQr`，解出**發票號碼、開立日期、含稅總額、買方統編、賣方統編**——但見 **W1**（單次 `jsQR` 漏右碼 `**` 接續） |
| 金額／日期／統編／號碼自動帶入 | ✅ 已有（`onFile` 裡 qr 有值就自動填，`deductible` 依買方統編 == 公司統編 判斷）——但見 **W2**（銷售額 `m[4]` 捕獲未回傳、稅額只靠費率回推） |
| **分類（這筆是什麼）自動帶入** | ❌ **沒有**——員工要自己在 `accountCode` 下拉選 |
| **紙本收據／手寫收據自動帶入** | ❌ **沒有**——無 QR 時只存照片，金額要手打，分類要手選 |
| **一整疊多張一次報** | ⚠️ 要一張一張點「＋再加一張」，無批次 |
| 送出後的伺服端把關 | ✅ 已有（可扣抵硬規則、發票查重、關帳鎖、自我核准擋）——**這層 agent 永遠碰不到，也不該碰** |

剩餘摩擦可拆成三塊：**① 分類候選 ② 紙本收據 OCR ③ 批次**。優先序仍待 W0 的實際摩擦
量測；下列順序是設計拆解，不是已證實的價值排名。

---

## 1. 切入點一：歷史分類候選（text-only，不須讓影像出外部）

### 1.1 現在怎麼做（傳統 ERP 手感）

員工拍完電子發票，號碼／金額／日期都自動帶好了，但「這筆是什麼」（餐飲／交通／
郵電／雜項…）還是要自己從一個白話分類下拉選。員工多半**不是會計**，常選錯——
而分類錯，跟著可扣抵性就錯（可扣抵性是「你稅法參數表登記的值＋依據」，系統預設未經查證、
可覆寫——見 `chart.ts:240-247`），直接影響進項稅。

### 1.2 帶入後

- 掃到 QR 後依賣方統編查該公司自己的歷史報銷，只顯示過去常用的 1–3 個分類與次數，
  **不自動選中**；沒有歷史就不給候選。
- 品名可填進 description，卻不能單獨決定分類：同一杯飲料可能是 `6112 員工伙食`、
  `6115 員工福利` 或 `6137 餐飲與交際`，差別在用途，不在品名。
- 候選仍有歧義時，agent 最多追問一句用途，最後由員工點選。冷啟動不讓 LLM 猜分類。

### 1.3 安全邊界

- **影像不出公司**：QR 解碼在瀏覽器端（jsQR），歷史候選不呼叫 LLM；若使用者另請 agent
  釐清用途，送的是最少必要純文字，不是照片。
- **不碰錢的欄位**：金額／日期／統編／號碼是 QR 所載的結構化值，parser 尚未驗證 24 碼
  加密驗證資訊，因此仍要讓人核對，不能稱為已驗真的權威值。
- **伺服端硬規則不能判斷用途**：`prepareItems` 只能檢查憑證形狀與該分類的參數，無法知道
  員工實際用途；所以歷史資料只能列候選，不能把錯分類寄望伺服器攔下。

### 1.4 需要的改動（最小集）

1. 先完成 W1 的左右 QR 合併，再擴充回傳品名明細；不能以「右碼暫不追」建立 v1。
2. 新增依 `sellerTaxId` 統計歷史分類的確定性查詢，回傳候選與次數，不呼叫 LLM。
3. 報銷頁顯示候選按鈕；只有使用者主動要求釐清用途時，才把必要的純文字送進 agent。

## 2. 切入點二：紙本收據 OCR（可能的真摩擦；需由 W0 量測，且有資料出外部決策）

### 2.1 現在怎麼做

無 QR 的收據（計程車、餐飲手寫單、雜支）目前 `onFile` 只做「存照片＋提示手動填」，
金額、分類、日期**全部手打**。這是報銷裡剩下最「傳統 ERP」的一格。

### 2.2 agent 帶入後

- 拍紙本收據 → agent（**多模態 vision**）辨識**金額、日期、品名／賣方** → 備好草稿
  （維持現行 `docType:"receipt"`、`deductible:false`；這是系統形狀，不是稅法斷言）→
  員工**核對金額與日期**後送出。
- 辨識不確定的欄位（金額模糊、日期手寫）**一律留白並問**，不猜（soul.md 底線三的延伸）。

### 2.3 安全決策點（已收斂，見 README Q1／plan C-4）

紙本收據 OCR 需要把**照片**送進 LLM endpoint；若 endpoint 在外部，照片就會**離開公司**。
收據可能含個人消費足跡（地點、時間）。這跟本 repo 對 `PII_KEY` 的態度同調，預設應是：

- **預設關閉** vision 收據 OCR（未開 = 維持現狀「手動填」，跟「未設 `PII_KEY`＝維持既有
  形狀＋出聲提醒」同一條紀律）。
- 由**管理者在設定頁開關**，並在開啟時明示「收據影像將送往外部 AI 供應商辨識」。
- QR 路徑（切入點一）**不受此開關影響**——它根本不出外部。

### 2.4 需要的改動

- OCR 建議服務需支援多模態 provider payload；目前可重用／抽出三個 body builder
  （`anthropicCall`／`openaiCall`／`geminiCall`，涵蓋多個 provider 名稱），但不必把影像加進一般
  chat turn 或暴露成 agent tool。
- 報銷頁提供「OCR 建議」按鈕，呼叫專用的**純建議端點**；端點回傳欄位候選，不建立
  `expense_claims`／`expense_items`。結果只填入目前頁面的 `DraftItem[]`，由人核對後按「送出」
  才真正 `POST /expense-claims`。

> ⚠️ 若草稿工具直接 `POST /expense-claims` 就是「送出」（status=submitted），會立刻進
> 財務的核准佇列——那不是草稿。所以草稿要停在**前端表單**，不是打 API。這是這條設計
> 跟 `create_quote`（打 `/quotes` 落地成真單）最關鍵的差別，審閱時請盯這點。

## 3. 切入點三：整疊批次（UX，不是 AI）

- 現在「＋再加一張」要一張一張點、一張一張上傳。
- 改成**一次選多張照片**，逐張跑既有 `readReceiptImage`（QR 的自動帶、無 QR 的進草稿），
  一次生成 N 筆 `DraftItem`，員工逐筆補分類／確認。
- 這條不涉及 agent，但不是零風險：需限制張數／總大小、有限併發、逐張進度與局部失敗重試，
  否則原尺寸 canvas 與 base64 payload 會造成記憶體尖峰或整批失敗。實際省時幅度由 W0 量測。

## 4. 資料流總結

```
拍照（瀏覽器）
 ├─ 有 QR → jsQR 解碼（憑證所載：號碼/日期/金額/買賣方統編）＋擴充解品名
 │           → 查歷史賣方分類候選（確定性、不自動選中）
 │           → 員工確認分類 → 送出（走既有 POST /expense-claims，伺服端全套把關）
 └─ 無 QR → 收據照片（若管理者開 vision）→ agent vision OCR → 金額/日期/品名草稿
             → 員工核對（不確定欄位留白）→ 送出（同上）
```

送出之後的核准／付款／作廢流程**完全不動**，仍由財務在畫面上按，agent 一律無門。

## 5. 分階段

| 階段 | 內容 | 風險 | 依賴 |
|---|---|---|---|
| **先行候選** | 切入點一（歷史候選，text-only）＋切入點三（多張批次） | 低至中 | W0 量測、W1 QR 正確性與批次護欄 |
| **之後** | 切入點二（紙本 OCR，vision） | 中（資料出外部） | 管理者開關 + agent 多模態管線 + 草稿停在表單 |

---

## 6. 審閱結論與剩餘前置

1. **品名從哪來**：先做左右 QR 合併，能解就填 description；解不到就留白。vision 僅在管理者
   對實際 endpoint 明示開啟後使用，且品名不直接決定分類。
2. **草稿停在表單的形態**：已收斂為報銷頁內的「OCR 建議」按鈕呼叫純建議端點，回傳結構
   填進當頁 state；不做會直接 POST 的 `create_expense_claim_draft` agent tool。
3. **分類建議要不要連「說明 description」一起填**：品名本身可以當 description（「星巴克-
   大杯拿鐵」），省一格。要。
4. **vision** 已收斂為預設關閉、同意綁實際 endpoint；**MCP 紅線**已由既有 decision 定方向，
   尚待工具面與 proposal／accept 契約實作。
