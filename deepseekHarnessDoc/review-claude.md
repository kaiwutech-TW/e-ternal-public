## 0. 一句話結論

**問題選得對，證據有一半沒站住，而最關鍵的一條安全結論（Q0）方向錯了。**

- 痛點地圖（A1 報銷、A3 對帳、B2 推播）我同意，優先序也同意。
- 但兩份設計的核心價值主張——「報銷已做掉一大半，只差分類建議」與「對帳讓 agent 推對應檔」
  ——**在實查後都不成立**：前者高估了現況（QR 解析有兩個真缺陷，其中一個會少抵稅、
  一個會多抵稅），後者的主要價值可以用**零 LLM 的確定性程式**拿到九成。
- Q0 的方向錯在：它把「紅線」定位成**工具清單**的問題。實查後，
  **刪掉 MCP 工具不會關上那道門**——門在 REST API，MCP 只是包裝。而 repo 的
  `README.md:36` 那句「核准過帳的門不存在」在今天是**假的**，這比 Q0 本身嚴重。

## 2. Q0（MCP 側與內建側的紅線要不要收齊）

### 2.1 結論：**要收齊，但 DeepSeek 定位錯了層——刪工具關不上門**

實查的因果鏈：

1. MCP 的每一個工具都只是 `client.post(...)` 到同一套 REST API（`apps/mcp/src/client.ts:54-59`，
   帶 `Authorization: Bearer …`）。
2. API 端收到金鑰後，`userFromApiKey` 把它解析成一個**與 session 使用者完全同形的 `AuthUser`**
   （`apps/api/src/services/api-keys.ts:56-81`），`app.ts:708-714` 之後就分不出這是人還是機器。
3. `authorize()` 只看 `role`（`services/auth.ts:464-477`）。所以
   **持有一把 finance/admin 金鑰的任何程式，都能直接打 `POST /expense-claims/{id}/approve`**，
   與 `tools.ts` 裡有沒有那個工具無關。

因此：**「從 `tools.ts` 刪掉 approve」＝把入口從選單上拿掉，不是把門鎖上。**
對純 MCP 客戶端（Claude Desktop 那類，模型只能呼叫 server 暴露的工具）它有效；
對任何有 shell／HTTP 能力的 agent harness 無效。這個差別必須寫清楚，
否則下一個人會以為刪完就安全了。

### 2.2 這裡有一條既有決策，DeepSeek 沒引用

`packages/db/migrations/0021_agent_access.sql` 檔頭「設計紀律一」已經定案：

> API 金鑰依附在使用者身上，不自成一套權限……要限制 agent 能做什麼，做法是
> **給它一個角色受限的專用帳號**，不是在金鑰上另外長出一套權限模型。

理由是「權限的單一事實來源，避免兩份定義漂移」。`docs/mcp.md:8-12` 也是這樣教使用者的。
**任何 Q0 的答案都必須先回應這條，否則會被正當地擋下來。**

### 2.3 但既有決策在「一人公司」情境下有一個破口

`expenses.ts:262-271` 的自我核准擋對 **admin 例外放行**，理由寫在註解裡：
「一人公司裡老闆本來就是自己核自己，擋死等於逼他建第二個帳號」。

把這條跟 0021 紀律一疊起來，會得到一個具體的風險鏈——而它正好命中本 repo 的目標使用者
（`260814` 紀錄的「一人軟體顧問公司」）：

> 一人公司只有一個 admin 帳號 → 金鑰只能開在 admin 上（開別的角色就什麼都做不了）
> → MCP 的 `approve_expense_claim` 對它全開 → **外部模型可以核准任何一張報銷單並拋轉費用傳票**，
> 而「給它一個角色受限的專用帳號」這個既有解法在這裡**沒有可用的角色可給**。

也就是說：0021 紀律一的解法**只對多角色公司有效**。這是它的真實射程，之前沒有人寫下來。

### 2.4 我的具體建議（三段，可分開採納）

**(a) 先修 `README.md:36` —— 這是最急的一件，且零風險。**
那句「責任紅線是結構不是自律——工具集只有讀取與草稿，核准過帳的門不存在」
在今天不成立（`tools.ts` 有三個寫入動作；API 層對金鑰全開）。
一份開源專案的 README 對安全模型的宣稱是假的，比功能缺口嚴重。
兩條路擇一：把句子改成它做得到的（例如「內建助理的工具集只有讀取與草稿；
MCP 側的權限跟隨你發給它的帳號角色」），或把它變成真的（走 (c)）。
**在 (c) 落地之前，README 那句話必須先改。**

**(b) 定義「人類專屬動作」清單，作為單一事實來源。**
建議至少含：報銷 `approve`/`reject`/`pay`/`void`、各單據 `void`、月結關帳、
發票作廢、發薪定案。這份清單放在 `packages/core`（與 `ROLE_PAGES`／`SYSTEM_ACCOUNT_CODES`
同一個「清單只寫一次」的紀律），**內建側與 MCP 側都從它推導**，而不是各寫一份。
`ship_order` 與 `convert_quote` 我**不主張**放進去（它們是業務日常，且覆述-確認可以處理），
但這是主導者的取捨，不是我的。

**(c) 若要「結構不是自律」名符其實，唯一有效的落點是 API 層。**
做法：`app.ts` 認證時記下「這個請求是金鑰來的」（`c.set("viaApiKey", true)`），
`authorize()` 對 (b) 的清單在金鑰請求下 **default-deny**。

要點——**這不違反 0021 紀律一**，理由要寫進 migration 檔頭給下一個人看：
紀律一擋的是「在金鑰上長出一套**會與角色定義漂移**的 scope 模型」；
而這裡加的是一個**只能收窄、不能放寬、無參數、無 per-key 設定**的旗標。
它不新增任何「誰能做什麼」的定義，只是在既有答案上再減一次。沒有第二份會漂移的定義。

代價要誠實講：一人公司的 admin 就**不能**再用 agent 核准報銷了，得自己開畫面按。
我認為這正是「責任紅線」四個字的意思——但它是產品取捨，**留給主導者拍板**。

**(d) 補一條測試**：目前 `soul.md` 那份「先覆述再做」的清單與 `AGENT_TOOLS`／`tools.ts`
之間沒有任何機械連結，兩邊漂移不會有人發現（第 1 條、第 3 條的錯誤就是這麼來的）。
(b) 落地後應該有一條測試斷言「人類專屬動作清單 ∩ 任一側工具集 = ∅」。

## 3. Q1（收據影像出外部 LLM 的預設）

### 3.1 結論：同意「預設關閉」，但**開關掛錯地方了**

DeepSeek 把開關設計成「vision 收據 OCR 的 on/off」。實查後這個切法不對：

`agent-chat.ts:406-434` 的 provider 有 **anthropic／openai／azure-openai／google／vertex-ai／
ollama／custom** 七種，其中 **ollama 與 custom 可以是自架的**（`:432` 明寫要填 Base URL）。
也就是說「開 vision」≠「資料出外部」——**自架模型的 vision，影像根本沒離開公司**。

所以正確的維度不是 `vision on/off`，而是：

> **「這個 provider 的端點在不在我們自己手上」**。

建議形狀（與 `PII_KEY` 那條紀律同構，也與 `docs/deployment.md` 的對照表同一個講法）：

| 情況 | 行為 |
|---|---|
| provider 為自架（ollama／custom 指向內網） | vision 可開，**但仍要在畫面上說一次影像會送到哪個端點** |
| provider 為外部雲端 | **預設關閉**；管理者要開，必須看到具名提示「收據影像將送往 〈供應商名〉 辨識」並自己按下去 |
| 未設定 | 維持既有形狀（手動填）＋**出聲**，絕不靜默降級 |

### 3.2 兩點補充

1. **QR 路徑不受影響**這句我同意，且它比 DeepSeek 講的更強：QR 解碼在瀏覽器端
   （`einvoice-qr.ts:101` jsQR），連伺服器都沒經過。
2. **但收據照片本來就已經上傳到自己的資料庫了**（`Expenses.tsx:133` `image: l.image`，
   縮圖 base64 進 DB）。所以 Q1 真正的界線不是「照片會不會離開瀏覽器」，
   而是「照片會不會離開**我們的機器**」。DeepSeek 的敘述（「收據照片不上雲」）
   在 QR 路徑下容易被讀成「照片沒存下來」，建議改寫精確一點。

## 4. Q2（B1／B2／C1／C2 要不要展開、誰認領）

### 4.1 我的排序與理由

| 條目 | 我的判斷 | 理由 |
|---|---|---|
| **B2 主動推播** | **展開，我認領** | 資料端已經全部就緒，是四條裡投入最小、風險最低（純讀）、感受最強的 |
| **C1 月結預檢** | 展開，但排在 B2 之後 | 同為純讀、零動帳；但它要先盤點「哪些檢查項有現成端點」，工作量大於 B2 |
| **C2 導入 wizard** | 暫緩 | 價值真實（決定有沒有人願意開始用），但它的前提是「SOP 順序錯了會炸」那個缺口先修——那是本體問題，不是 agent 問題 |
| **B1 銷售 chain** | **反對現在展開** | 它是唯一一條要把「多張會動帳的單據串成一條 agent 驅動流」的設計。在 Q0 的門還沒關之前展開它，等於在紅線未定的地基上蓋最重的那棟 |

### 4.2 我認領 B2 的大綱（不在本次落地，只寫形狀）

**觀察**：B2 其實已經做掉一半了。`0047` 已經有首頁「還沒做完的事」卡，
且 `agent-chat.ts:78-82` 的 `api_get` 說明裡已經列了
`/contracts/billing-due`、`/contracts/expiring`、`/recurring-payables/due`。
缺的不是資料，是**送達**。

大綱：

1. **一個純讀的彙總端點**（把首頁那張卡的資料源集中成一個 `GET`），
   agent 與畫面共用同一份——不要讓 agent 自己拼四個端點再自己算，那會長出第二套邏輯。
2. **送達通道由主導者選**：站內未讀、Email、或什麼都不做只在首頁顯示。
   這是產品決定，不是技術決定。
3. **文案紀律（這條是重點）**：`api_get` 的說明已經寫死一句
   「**這些日期都是使用者自己設的，不是法定期限；系統不知道也不得推測任何申報或繳費時間**」
   （`agent-chat.ts:80-82`）。主動推播是**最容易破這條**的功能——
   「今天你該做這 5 件事」天生就像在講期限。所以推播文案必須逐句標明來源
   （「你設的付款日是 X」而不是「今天要繳 X」），並且**不得包含任何系統沒被告知的日期**。
4. 排程：`golden` 的教訓（`TRAPS` 的匯出時點漂移）提醒一件事——推播內容要記下
   「這是依哪一天的資料算的」，否則使用者事後對不上會以為系統錯了。

## 5. 報銷設計逐條（`expense-claims-agent.md`）

### 5.1 第 0 節「已做掉一大半」——**高估了，而且掩蓋了兩個真缺陷**

實查 `einvoice-qr.ts` 與 `Expenses.tsx:88-113` 後，發現兩件現況表格沒講的事。
它們都不是「還沒做的功能」，是**已經做了但會出錯的地方**——比缺功能嚴重。

**缺陷 A：`jsQR` 一次只回一個碼，而證明聯有兩個 QR。**
`einvoice-qr.ts:101` 呼叫一次 `jsQR(...)`，取到哪一個碼由影像決定。
右側 QR 以 `**` 開頭（見同檔 `:32-39` 的規格註解與 `:63` 我方產碼的實作），
`parseEInvoiceQr` 對它會回 `null`（`:17` 的正則比不中）→ 整張發票掉進
「未偵測到電子發票 QR，請手動填金額」的分支（`Expenses.tsx:107`）。

後果：使用者拍了一張**有效的電子發票**，系統告訴他「沒偵測到，請手動填」，
而手動路徑的 `docType` 是 `receipt`、`deductible: false`——
`expenses.ts:136-141` 的硬規則會讓這筆**永遠不可扣抵**。
**這是一條會少抵進項稅的路徑，而且零徵兆**（畫面上只說「照片已存」，不說「你可能拍到右邊那個碼」）。

> 這一條同時把 DeepSeek 切入點一的地基抽掉了：**品名接在左碼後段、放不下才續到右碼**，
> 而現在的管線連「確定拿到左碼」都做不到。品名解析必須先解決「一張影像掃出多個碼」，
> 不是「擴充 `parseEInvoiceQr` 的回傳值」而已。

**缺陷 B：QR 裡有權威的未稅銷售額，但系統丟掉它、改用稅率回推。**
`parseEInvoiceQr` 的正則 `m[4]` 就是銷售額（未稅，見 `:5` 的欄位註解），
但回傳值裡沒有它（`:22-28` 只回 5 個欄位）。
於是 `expenses.ts:156-161` 只能用 `amount - roundHalfUp(amount / (1 + vat.rate))` 回推。

兩個後果：
- **捨入殘差**：回推值與發票自己印的稅額可能差 1 元，而這個數字會進 401 的進項。
- **更嚴重的**：若某張發票的 QR 上「銷售額 == 總計額」（＝這張發票自己說它的稅額是零），
  現行回推**仍會依稅率算出一筆稅**。這是**多抵稅**的方向。

  ⚠️ 我不對「哪些交易稅額為零」做任何法規判斷——上面說的完全是**發票自己的兩個欄位相減**。

  建議做法也不要讓任一方靜默勝出：**兩個數字不一致就出聲，請人確認**
  （與 `expenses.ts:205` 那句「走了回退費率而不說，等於系統替使用者做了一個他不知道的決定」同一個紀律）。

**這兩條我建議排在 DeepSeek 全部三個切入點之前。** 它們不需要 agent、不需要外部呼叫、
可以寫成單元測試，而且修的是「錯了零徵兆」的東西——正好是這個 repo 一向優先處理的形狀。

### 5.2 切入點一（分類建議）——**同意問題，不同意解法**

問題（員工不是會計、選錯分類會連帶影響可扣抵）真實，我同意它是報銷剩下最大的一格。
但「品名 → 分類」這條路我認為**在最常見的案例上不可判定**：

DeepSeek 自己舉的例子就證明了這點。「星巴克-大杯拿鐵 135 元」該進哪一格？
看 `chart.ts:259-270`：**6112 員工伙食**（加班餐費）、**6115 員工福利**（部門聚餐）、
**6137 餐飲與交際**（請客戶）都可能——而這三個的 `inputTaxDeductible` 預設**不同**
（true／true／false）。

決定分類的是**用途**（誰喝的、為了什麼），而用途**不在 QR 裡、不在照片裡、
只在員工腦袋裡**。把它交給 LLM 猜，就是拿一個它沒有資訊的問題去要一個看起來很篤定的答案
——而錯誤會沿著 `inputTaxDeductible` 一路走進 401。

**替代方案（我建議取代切入點一的 MVP）：用歷史選擇做確定性建議，零 LLM。**

- `expense_items` 已經存了 `sellerTaxId`（`Expenses.tsx:132`、`expenses.ts` 明細）。
- 掃到 QR 後，查「這個賣方統編，公司過去最常選哪個分類」→ 直接把那格帶好，
  並顯示「這家你前 12 次都選 6133 文具與辦公用品」。
- 優點：零外部呼叫、零成本、**可寫測試**、可解釋、會隨公司習慣自我校正、
  而且**冷啟動時它會誠實地什麼都不建議**（沒歷史就不猜）——比 LLM 的「總是給一個答案」安全。

**LLM 該用在哪裡**：不是猜答案，是**問對問題**。若歷史沒有共識（同一家店三種分類都出現過），
那才是 agent 上場的時機——問一句「這筆是自己吃、部門聚餐、還是請客戶？」，
把三個選項連同代號攤開讓人點。這才是它真正比下拉選單強的地方。

**因此我對 `suggest_expense_category` 這個 tool 的態度**：先不要做。
先做歷史建議（純前後端），量出「還有多少比例的單需要問」，再決定要不要為那個殘餘量
新增一個 agent 工具。

### 5.3 切入點二（紙本 OCR）——同意方向，見第 3 節的開關修正

補一點 DeepSeek 沒提的：紙本收據路徑目前**硬編死** `deductible: false`
（`Expenses.tsx:107`）。這在「收據無進項稅」的前提下是對的，
但一旦 vision 上線、辨識出「這其實是一張有統編的電子發票只是 QR 拍糊了」，
就會與缺陷 A 撞在一起。**vision 上線前，缺陷 A 必須先修**，否則兩條路會互相掩蓋。

### 5.4 切入點三（批次）——**完全同意，且我認為它該排第一**

理由比 DeepSeek 講的更強：它零 LLM、零安全決策、零新紅線，
純粹是 `readReceiptImage` 跑 N 次＋生成 N 筆 `DraftItem`（`Expenses.tsx:56`）。
「10 分鐘變 1 分鐘」的效果不需要任何 agent 就能拿到。
**把它排在需要拍板的東西前面，可以在紅線討論期間先交付價值。**

### 5.5 未決問題逐條

1. **品名從哪來**：先修缺陷 A，否則此題無意義。修完之後，解析品名還有兩個
   DeepSeek 沒提到的障礙：(i) 明細段前面有一個**編碼參數**欄（`einvoice-qr.ts:61` 我方固定寫 `1`，
   註解只說明 `1=UTF-8`）——**其他值代表什麼編碼，我未查證，實作前必須拿規格核對**，
   猜錯會解出亂碼；(ii) 品名本身可能含 `:`，我方產碼時會轉成全形（`:56`），
   但別家開票軟體不保證這麼做，解析要能容錯。
   **結論：v1 承認「品名取不到就不建議」是對的**，我同意 DeepSeek 的傾向。
2. **草稿停在表單的形態**：見第 7.1 節——我的答案是「**都不要**，改走專用端點」。
3. **description 要不要一起填**：同意填，但**來源限定為 QR 的品名原文**，
   不要讓 LLM 改寫。description 是之後會計重分類時唯一的線索，
   被潤飾過的文字會失去證據價值。
4. Q0／Q1 見第 2、3 節。

## 6. 對帳設計逐條（`bank-reconciliation-agent.md`）

### 6.1 切入點一（agent 推匯入對應檔）——**九成可以不用 LLM**

DeepSeek 說「LLM 對『從例子推斷 schema』是強項」。這句話對，
但它跳過了一個問題：**這件事確定性程式也做得到，而且做得更好。**

要推斷的東西是：日期欄在哪（`115/07/05` vs `2026-07-05`）、金額是一欄帶正負還是收支兩欄、
編碼是 Big5 還是 UTF-8、摘要欄、餘額欄。這些全都是**可以用正則與統計判斷的**，
而且確定性版本有三個 LLM 拿不到的好處：

- **可重現**：同一個檔案永遠推出同一份對應檔。LLM 不保證。
- **可測試**：拿到一份新銀行的檔就補一條測試，涵蓋率會單調上升。LLM 沒有這個累積。
- **零資料外流**：整個 Q2（樣本去識別化）的問題**直接消失**。

**而且 DeepSeek 的 Q2 自我矛盾**：它建議「預設只送表頭＋欄位形狀，不送完整交易列」——
但「民國還是西元」「Big5 還是 UTF-8」「一欄帶正負還是兩欄」**全部都只能從資料列看出來，
表頭一個字都不會講**。照它的預設做，agent 剛好推不出它被找來推的那幾件事。

**我的建議**：
1. 先寫**確定性 sniffer**（純函式、無外部呼叫）產出一份對應檔草稿，使用者逐項確認。
   這完全符合 spec 邊界 1「對應檔是資料不是程式」。
2. LLM **只在 sniffer 拿不準的欄位**上當 fallback，而且送出的是
   **欄位摘要**（型別＋樣本形狀，如「這欄長得像 `115/07/05`」）而非原始交易列。
   這樣既拿得到判斷所需的形狀，又不送出金額與對象。
3. 若 (2) 的殘餘量在真實檔案上很小，這條 agent 功能就**不必做**。

### 6.2 切入點二（比對敘事）——同意，但有一個被跳過的前提

同意「agent 只產敘事、不點確認」。
但 DeepSeek 的敘事範例（「建議沖銷貨單 #12＋#13」「對象對不上」）**假設了引擎已經存在**，
而引擎**未動工**。所以這條的真實依賴是「本體做完」，不是「golden sample 到手」。
排序時不要把它跟切入點一放在同一批。

「對帳的『確認』與『核准過帳』同級，只有人能按」——**強烈同意，而且這條應該寫進第 2.4(b)
的人類專屬動作清單**，在本體動工的**同時**就寫進去，不要等功能做完再回頭補紅線。

### 6.3 切入點三（`draft_journal_entry`）——見第 7.1，我反對做成 agent tool

### 6.4 未決問題逐條

1. **golden sample 到手前能不能動工**：**可以，但範圍受限。**
   確定性 sniffer（6.1）與明細列 append-only 的儲存結構，都不需要樣本就能寫——
   它們的形狀由「不寫死任何銀行格式」這條紀律決定，不由某一家銀行決定。
   **需要樣本的是「驗收」，不是「動工」**。我建議把 STATE 那條「等 golden sample」
   從**動工前提**改成**驗收前提**，並在沒有樣本前不宣稱這個功能可用。
2. **樣本去識別化預設**：見 6.1——DeepSeek 的答案自我矛盾。我的替代方案讓這題大部分消失；
   殘餘部分的預設是「送欄位摘要，不送交易列」。
3. **xlsx**：同意正交、照 spec 待定。無異議。
4. **引擎輸出要不要加 `confidence`／`anomaly` 欄位**：**加 `anomaly` 類的結構化事實，
   不要加 `confidence` 分數。**
   理由：`anomaly` 可以是**確定性的事實**（「金額相同但對象不同」「同一金額在視窗內出現三次」）
   ——那是引擎算得出、測得了、使用者看得懂的。
   而 `confidence` 是一個**看起來精確的猜測**：0.87 的意思沒有定義、無法驗證，
   卻會直接影響人要不要按下確認。這個 repo 對「系統替使用者做了一個他不知道的決定」
   一向的答案是出聲而非給分數（`expenses.ts:205`）。**給分數就是在誘導確認**，
   而 spec 邊界 3 存在的全部理由就是不要誘導確認。
5. **`draft_journal_entry` 的草稿邊界**：見第 7.1。

## 7. 三個必盯點的裁決

### 7.1 「草稿 vs 送出」——DeepSeek 的防線**在架構上守不住**，建議換一條路

DeepSeek 說：草稿工具要「停在前端表單，不是打 API」。**方向對，但這個東西做不出來。**

實查 `agent-chat.ts`：工具在**伺服器端**執行（`:479-484`），結果是一段**文字**回給模型
（`ToolResultBlock`），前端只拿到 `steps`（工具名＋一句摘要，`:481`）。
**目前沒有任何通道能讓一個工具的輸出落進另一個頁面的表單。**
要做到 DeepSeek 描述的形態，得新增一個「UI 意圖」通道
（工具回傳結構化 payload → 對話 UI 解讀 → 導頁 → 填 state）——
那是一個新的前後端契約，不是「照 `create_quote` 的形狀再寫一個 tool」。

更麻煩的是：**這條防線是靠實作紀律維持的**。`TOOL_POST_PATH`（`agent-chat.ts:186-189`）
是一張兩行的表，任何人多加一行 `create_expense_claim_draft: "/expense-claims"`，
草稿就變成 `submitted` 的真單，而且**不會有任何測試失敗**。
DeepSeek 自己標了這個雷，但它給的對策（「審閱時請盯這點」）是自律，不是結構。

**我的替代方案：不要把「產草稿」做成 agent tool。**

改成：報銷頁／傳票頁上一個**明確的按鈕**，打一個**專用端點**
（例如 `POST /expenses/suggest`），端點內部才呼叫 LLM，回傳純建議結構，前端填進表單。

這一招把整條風險**從架構上移除**：
- 這個端點**沒有寫入路徑**，它連 `TOOL_POST_PATH` 都不在，不存在「多加一行就變真單」的可能。
- 它不進 `AGENT_TOOLS`，所以**內建 agent 與外部 MCP 模型都拿不到它**——
  不必再擔心模型自己決定去建草稿。
- 使用者的心智模型也更清楚：他是在報銷頁上按「幫我看這張」，
  不是在對話框裡讓 agent 「幫我開一張」。**按鈕天然就是那個確認閘門。**

代價：失去「用一句話報帳」的對話體驗。我認為在報銷這個場景這不是損失——
使用者手上拿著一張紙，他要的是「少填幾格」，不是「跟人聊天」。

### 7.2 「確認對上」與「核准過帳」是否同級——**同意，且要現在就寫進清單**

見 6.2。補一句：spec 邊界 3 的理由是「錯了零徵兆」。
凡是符合「錯了零徵兆」這個特徵的動作，都該進 2.4(b) 的人類專屬清單——
這比逐條列舉更能防止清單漏項。建議把這句寫成清單的**收錄準則**。

### 7.3 「已做掉一大半」屬不屬實——**不屬實，見 5.1**

有做的部分是真的做了（QR 掃描、自動帶入、伺服端硬規則都在）。
但「一大半」這個評價掩蓋了兩條會直接影響進項稅、且錯了零徵兆的缺陷。
**建議 DeepSeek 把第 0 節的現況表改寫**：把「✅ 已有」改成「✅ 已有，但見缺陷 A／B」。
